# DataForge Entra 权限演示交接

## 目标

使用两个真实的 Microsoft Entra 用户演示同一工作区的权限差异。DataForge 不在前端提供虚假的角色切换，也不保存测试用户密码。

## 账号准备

1. 由具备 Entra 用户管理员权限的人员创建或选择第二个测试用户。
2. 在 DataForge 当前工作区中，将主讲账号保留为 `owner` 或 `admin`。
3. 将第二个账号作为显式成员加入工作区，角色设为 `viewer`；也可以把它加入已映射为 `viewer` 的 Entra 组。
4. 不要把测试用户密码、临时访问口令或对象 ID 写入仓库、截图或演示数据。

> Azure 订阅 Owner 不是 Entra 目录管理员。若当前账号只能管理订阅资源，账号创建和目录组成员调整仍需租户管理员完成。

## 演示流程

1. 在正常浏览器中以主讲账号登录，打开“设置 → 模型与生成 → 身份与访问”。
2. 确认“当前登录身份”显示 Microsoft Entra ID、工作区所有者或管理员，以及实际授权来源。
3. 在无痕窗口访问同一生产域名，以第二个 Entra 用户登录。
4. 打开同一工作区，确认“当前角色”显示工作区查看者。
5. 验证查看者可以读取被授权的业务内容，但不能修改模型路由、模型提供商治理、成员角色或生产动作。
6. 关闭无痕窗口结束第二账号会话；不要在浏览器中保存密码。

## 可复核接口

- `GET /api/auth/session`：只返回友好姓名、邮箱、身份提供方和可信来源，不返回对象 ID、租户 ID、组声明或原始令牌。
- `GET /api/workspaces/{workspace_id}/access`：返回该工作区的服务端角色判定和安全原因码。
- `GET /api/workspaces/{workspace_id}/governance/capabilities`：返回各治理功能的服务端权限，不依赖前端按钮隐藏。

## 验收边界

- 生产页面不能把 Entra 登录用户显示为 `local` 或 `Demo User`。
- 第二账号的角色必须来自服务端访问决策，不能由浏览器参数或本地存储切换。
- 角色变化后需重新登录或刷新访问判定；旧页面不能继续执行已失去权限的写操作。
- `DF_FINOPS_ACTIONS_ENABLED` 保持关闭，除非另行完成生产动作验收并获人工批准。
