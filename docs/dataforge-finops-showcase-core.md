# DataForge AI 运营与 FinOps 展示核心说明

更新日期：2026-08-03
适用对象：IT 管理者、AI 平台团队、运营负责人、财务人员
适用范围：DataForge `demo-corpus` 展示工作区与本次 FinOps 治理分支

## 1. 展示定位

DataForge 不是把运行记录拆成更多报表，也不是只展示一张模型账单。它要把每一次 AI 调用转化为可见、可归因、可审阅、可治理的经营事实，让 IT 与财务可以在同一套口径中回答四个问题：

1. 当前 AI 使用规模、成本和服务质量是否正常？
2. 消耗由哪个部门、工作区、Agent 和模型产生？
3. 投入是否产生了可验证的业务价值？
4. 哪些风险应该优先处理，判定依据和请求证据是什么？

一句话介绍：

> DataForge 将模型用量、成本、业务归因、效能、ROI 与风险证据放进同一条运营链路，让团队不仅知道发生了什么，也知道下一步应验证什么。

## 2. 为什么需要这套能力

客户真正面对的并不是“看不到 Token”，而是以下四类运营问题：

- **成本无法解释**：总账单不能说明是哪一个业务、工作区、Agent 或模型造成了变化。
- **效能与成本割裂**：Token、时延、错误率、缓存和成本分散在不同视角，无法判断节省是否牺牲了体验。
- **风险发现太晚**：失败重试、慢请求、未计价调用和异常用量往往在影响已经发生后才被发现。
- **优化无法验证**：没有统一的前后对比与请求证据，很难说明模型路由、上下文精简或缓存优化是否真的有效。

DataForge 提供四层共同语言：

| 层次 | 回答的问题 | DataForge 中的体现 |
| --- | --- | --- |
| 可见性 | 现在用了多少，运行得怎样？ | Token、请求、估算成本、时延、错误率、缓存与趋势 |
| 可归因 | 谁在使用，为谁服务？ | 部门、工作区、人员、Agent、模型与任务维度 |
| 可问责 | 谁应该理解并处理这个问题？ | 授权范围、风险域、证据对象与责任范围 |
| 可治理 | 如何判断、验证并持续改善？ | 风险扫描、请求证据、AI 解读、建议与人工复核 |

## 3. 产品信息架构

DataForge 已经通过“工作区、数据资产、会话、运行记录、分析产物”承接业务执行过程，因此运营能力保持聚焦：

- **成本管理**：运营总览、成本分析、效能与 ROI。
- **风险与优化**：只读风险扫描、判定依据、请求证据、AI 解读和优化建议。
- **运行记录**：继续保留逐次 Agent 执行、状态和返回会话能力，不被 FinOps 页面替代。
- **设置**：承接模型提供方、Agent 模型分配、官方价格映射、预算和通知配置。

客户界面使用“统一入口”“入口覆盖”“请求对账”等业务语言，不把底层网关产品名直接作为指标标题。

## 4. 建议演示主线

### 4.1 开场：从业务工作区进入运营视角

先展示工作区、数据、会话、运行记录和产物仍然存在，然后进入“成本管理”。说明运营页面不重复业务内容，而是把跨请求的使用事实聚合成管理判断。

建议话术：

> 前面的工作区回答“业务做了什么”，这里回答“这些 AI 能力用了多少、由谁产生、运行得怎样、是否值得，以及哪里需要治理”。

### 4.2 成本管理：先形成一屏判断

展示运营总览中的核心指标：

- 请求量与 Token 规模；
- 官方价格口径下的估算成本；
- 成功率、错误率、P50/P95 时延；
- 缓存命中、避免 Token 和估算节省；
- 统一入口覆盖与未计价请求；
- 成本、调用、Token 与时延趋势。

图表必须按真实数值比例绘制，柱高、折线、饼图占比和纵轴不能使用等高占位。鼠标或键盘聚焦某个数据点时，浮层需要展示该点的指标、单位、时间或维度，并保持在视口内。

建议话术：

> 这不是单独看费用，而是把规模、成本、体验和数据完整性放在同一个判断画面中。成本下降但错误率上升，不能被解释为一次成功的优化。

### 4.3 成本分析：解释钱花在哪里

切换到“成本分析”，按部门、工作区、Agent 和模型查看请求、Token、估算成本、错误率、P95 与缓存命中率。

重点说明：

- 同一个工作区最多归属一个部门，避免重复分摊；
- 模型成本根据当前激活的官方价目版本估算；
- 无法可靠匹配价格的请求显示“未计价”，不会伪造为零；
- 可从模型或 Agent 维度继续进入设置，调整模型关联或价格映射。

### 4.4 效能与 ROI：区分投入价值和已验证结果

展示价值桥、证据成熟度、单位经济趋势和 ROI 情景。

演示时必须使用三种状态：

- **观测事实**：请求、Token、模型估算成本、产物数量等系统已经记录的事实；
- **情景测算**：人工设置的月度收益、时间价值、实施成本等假设；
- **已验证结果**：经过业务负责人独立确认并关联结果事件的业务成效。

建议话术：

> DataForge 可以自己完成 ROI 情景测算，但不会把假设直接包装成已实现回报。只有成本证据和业务结果都完成验证，页面才会给出可复核 ROI。

### 4.5 风险与优化：主动运行一次只读扫描

从左侧进入“风险与优化”，点击“执行风险扫描”或“重新扫描”。强调该动作只在当前授权工作区和筛选范围内重新执行确定性规则，不扫描云资源，也不修改生产配置。

扫描需要展示：

- 最近扫描时间与筛选范围；
- 请求样本数量；
- 检查规则数与发现数；
- 证据覆盖率；
- 策略版本；
- 每条规则的观测值、阈值、样本数、判定原因和建议。

七项默认运营检查：

| 规则 | 主要判断 | 展示重点 |
| --- | --- | --- |
| 调用失败率 | 错误率超过策略阈值且样本足够 | 失败类别、模型和代表请求 |
| P95 响应时延 | P95 超过体验阈值且样本足够 | 慢请求、模型路由和处理阶段 |
| 日成本预算 | 估算成本进入提醒或关键区间 | 成本贡献来源，不执行自动限流 |
| Token 异常增长 | 当前时段高于历史基线倍数 | 高上下文、重复调用或重试 |
| 统一入口覆盖 | 入口治理覆盖低于目标 | 未纳管或关联状态未知的调用 |
| 未计价请求 | 未计价占比超过阈值 | 缺失的模型与价格映射 |
| 缓存命中率 | 可缓存请求达到样本要求但命中偏低 | hit、miss、bypass 与可避免 Token |

样本不足时显示“样本不足”，不能为了填满页面生成风险。

### 4.6 查看证据：每一个判断回到自己的请求

选择某条风险后点击“查看证据”。证据抽屉应只展示支持当前判断的请求，而不是统一回退到最近请求列表。

客户首先看到友好的业务名称，例如“客户机会分析 · 慢响应”；技术标识折叠在详情中，需要进一步排障时才展开。证据内容包括：

- 当前风险相关的观测指标；
- 工作区、Agent、模型和业务操作；
- 请求状态、错误类别、时延和 Token；
- 缓存命中、未命中或绕过状态；
- 估算成本及计价状态；
- 安全的用户问题与可见回答摘要；
- 必要的请求关联键和运行关联信息。

失败率、慢请求、缓存、Token、未计价和入口覆盖必须打开不同且语义匹配的请求证据。

### 4.7 问 AI：让解释跟随当前指标

在某个指标或风险项上点击“问 AI”。系统应根据点击位置自动生成问题并立即发送，不要求用户重新描述上下文。

AI 回答按以下结构呈现：

1. **结论**：当前信号是否需要关注；
2. **依据**：使用了哪些观测值、阈值、样本和请求证据；
3. **影响**：可能影响成本、体验、效率还是治理；
4. **建议**：下一步如何验证，而不是直接修改生产；
5. **边界**：哪些仍是估算、部分证据或待验证内容。

AI 只能解释和提出建议，不能修改规则判定，也不能批准或执行生产动作。AI 会话按工作区保存并支持跨设备读取；打开浮窗时优先使用已有缓存，不阻塞当前咨询。

### 4.8 设置：说明成本口径如何形成

最后进入设置，展示 Agent 模型分配、外部模型接入、官方价格映射、预算和通知入口。

重点说明：

- 一个 Agent 可以由管理员选择允许的模型；
- 模型调用按实际使用的 provider、deployment 和价目版本进入统计；
- 提供方密钥只写入受控配置，前端不回显；
- 价格匹配失败时保留“未计价”状态，并允许管理员补充映射；
- 预算提醒可以通知管理员，但当前展示不把预算等同于生产强制上限。

## 5. 从调用到决策的数据链路

当前 DataForge 的展示口径如下：

```text
业务工作区 / Agent
        ↓
统一模型调用入口与应用运行事件
        ↓
规范化、关联和请求对账
        ↓
Azure SQL 请求事实、聚合、价格、风险与扫描记录
        ↓
FinOps 查询 API
        ↓
成本管理 / ROI / 风险与优化 / 请求证据 / 运营 AI
```

- 应用事件负责工作区、Agent、人员和运行语义等高基数归因。
- 统一入口证据用于补充覆盖、Token、模型、状态和时延，并通过 correlation 与应用事件对账；同一调用不会重复累加。
- Azure SQL 是请求事实、价目、聚合和扫描结果的数据来源。
- Redis 只缓存有界查询结果，不是事实来源；页面使用缓存优先和后台更新，降低重复等待。
- 客户界面不需要理解底层产品名，工程详情中仍可保留必要的技术关联信息。

## 6. 隐私、安全与可信边界

演示必须同时说明以下边界：

- 成本是按官方模型价格和当前价目版本计算的估算值，不是 Azure 实际账单。
- 无可靠价格映射时显示“未计价”，不会将未知成本写成零。
- ROI 情景不等于已实现 ROI；业务结果未验证时必须明确标记。
- 请求事实不采集密钥、原始身份、system prompt、provider 原始响应和内部错误正文。
- 客户友好业务名称优先展示，技术 ID 只在详情中按需查看。
- tenant 与 workspace 范围由可信身份和服务端授权收窄，不能由客户端自行扩大。
- 正式页面继续使用既有 Entra / Easy Auth 边界；非正式公开页面不强行添加未配置的 Entra 白名单。
- 风险扫描是只读判断；`DF_FINOPS_ACTIONS_ENABLED=0` 时不会自动执行生产治理。

## 7. 演示工作区应具备的内容

`demo-corpus` 用于稳定展示理想能力，至少需要形成以下有区分度的样本：

- 多个部门、工作区、Agent 和模型的不同请求量与成本；
- 输入、输出、缓存和推理 Token 的不同结构；
- 已计价和未计价请求；
- 成功、4xx、5xx 和慢请求；
- 缓存 hit、miss、bypass 对照以及避免 Token、估算节省；
- 统一入口已覆盖、应用可见但未关联和未知状态；
- ROI 使用、产出、情景与待验证业务结果；
- 七项风险规则的可解释结果和互不重复的代表证据。

页面不需要向客户标注“演示数据”，但仓库和数据库内部应保留 seed batch 与 provenance，便于幂等更新和清理。非演示工作区不能补造固定风险或收益。

## 8. 现场展示成功标准

一次完整展示应让观众清楚看到：

1. 成本管理在一屏中回答用量、成本、质量和数据完整性；
2. 成本可以下钻到部门、工作区、Agent 和模型；
3. ROI 明确区分观测、测算和验证；
4. 风险与优化可以由用户主动运行一次只读规则扫描；
5. 每个风险展示观测值、阈值、样本、判定原因和建议；
6. 每个证据入口打开与当前指标语义一致的请求；
7. “问 AI”自动针对当前指标发问，并用结构化内容回答；
8. AI 建议可以继续下钻证据，但不会自动修改生产；
9. 图表按数值比例显示，浮层不被相邻卡片或视口裁切；
10. 页面刷新不频繁，缓存命中后可以快速切换，后台失败时保留最近一次成功结果。

## 9. Copilot 审阅清单

请 Copilot 基于当前分支同时审阅前端、后端和数据契约，而不是只看截图。

### 前端

- “成本管理”和“风险与优化”是否为独立导航，且刷新后立即出现；
- 桌面、1366、中间宽度和移动端是否无覆盖、裁切和横向溢出；
- 柱状图、折线和饼图是否根据真实数值比例绘制；
- tooltip、证据抽屉和 AI 浮窗是否保持在视口内；
- 七项风险是否都有观测值、阈值、样本、原因、建议和状态；
- 不同证据按钮是否打开不同且语义匹配的请求；
- 点击局部“问 AI”是否只自动发送一次对应问题；
- AI 回复是否稳定展示结论、依据、影响、建议和边界；
- 刷新、缓存、预加载和历史同步是否不会造成整页等待或覆盖新消息；
- 页面是否避免把底层网关产品名直接展示为客户指标。

### 后端

- 风险扫描是否只接受受控筛选范围，并要求 workspace owner/admin；
- tenant 与 workspace 是否始终从可信身份和服务端权限收窄；
- 七项规则是否执行最小样本判断，样本不足不生成异常；
- 扫描是否记录策略版本、账本版本、范围、样本、覆盖率和证据引用；
- 指标/策略证据选择是否语义匹配，而非统一取最近请求；
- AI 是否只能引用允许的证据，并且无法改变规则结论；
- SQL migration 是否 additive、幂等且不删除现有业务数据；
- 是否没有新增密钥、正文、原始身份或内部错误正文持久化；
- 是否没有绕过 `DF_FINOPS_ACTIONS_ENABLED=0` 创建或执行生产动作。

## 10. 收尾话术

> DataForge 的价值不是多展示几个 Token 图表，而是建立一套统一的 AI 使用事实：费用可以解释、责任可以归因、问题可以回到请求证据、ROI 不会越过验证边界、优化建议可以被复核。这样 IT、财务和业务团队才有共同的语言持续管理企业 AI。
