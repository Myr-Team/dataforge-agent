# 运营管理 ROI、风险与加载体验整改设计

## 1. 背景

DataForge 的工作区、数据资产、会话、运行记录和分析产物已经承担业务执行与追溯职责。运营管理不应再次拆分或复制这些内容，而应面向 IT 与财务人员回答三个经营问题：

1. 当前 AI 投入是否值得继续；
2. 当前最重要的成本、体验和治理风险是什么；
3. 下一步应该修改什么，以及如何验证改善。

本设计参考现有 Token 可观测性与 FinOps 宣讲材料中的统一事实、企业归因、证据下钻和持续优化主线。页面定位为经营决策入口，而不是产品能力目录或工程诊断控制台。

现有实现已经具备请求事实、估算成本、ROI 情景、异常、建议、分析结论和请求证据，但存在以下体验问题：

- ROI 页面重复展示相同状态，经营结论不突出；
- 情景测算、运行事实和已验证业务结果之间缺少清晰边界；
- 风险、异常、建议和 AI 解读并列堆放，主次关系弱；
- 建议停留在泛化文字，没有具体修改范围、验证标准和回滚方案；
- 页面虽有预加载和 Redis 查询缓存，进入页面仍会强制重新请求；
- ROI 和风险页签分别并发读取多个接口，切换页签不能稳定复用结果；
- 自动刷新和后端缓存周期重合，容易在缓存刚失效时触发慢查询。

## 2. 目标

### 2.1 产品目标

- 将“效能与 ROI”改造成投入、价值、证据和经营判断组成的决策闭环；
- 将“风险与优化”改造成风险态势、优先事项、证据、整改草案和改善验证组成的处置闭环；
- 使用少量 BI 图表解释价值构成、证据成熟度、风险优先级和优化组合；
- 提供客户可理解的能力与口径说明；
- 进入页面优先显示最近成功结果，避免重复等待和频繁整页刷新；
- 保持估算、观测和验证状态真实，不把情景测算包装成已实现收益。

### 2.2 技术目标

- 总览、成本、ROI 和风险分别拥有可复用的页签级查询快照；
- ROI 和风险页面分别由一个聚合决策接口提供首屏数据；
- 浏览器和服务端同时采用 stale-while-revalidate；
- Dashboard 优先读取 SQL 小时或日聚合，单次请求事实只用于证据下钻；
- 写操作只失效受影响的数据域；
- 相同查询合并在途请求，筛选范围变化时取消过期请求；
- 保留现有授权、价目表、异常、请求证据和治理动作边界。

## 3. 非目标

- 不接入 Azure 实际账单或 Cost Management 对账；
- 不自动确认客户已经实现业务收益；
- 不自动确认异常根因；
- 不让 Agent 批准或执行治理动作；
- 不允许客户端提交任意脚本、策略 XML、资源 ID 或执行命令；
- 不恢复独立审计或请求追踪门户；
- 不把提示词、模型原始响应、密钥、原始身份或内部错误正文写入运营数据；
- 不在页面自动刷新时调用分析 Agent；
- 不在本次整改中重新设计运营总览和成本分析的全部内容，除共享加载、缓存和状态组件外。

## 4. 设计原则

### 4.1 先结论，后证据

首屏先告诉用户“当前判断是什么”，再说明依据、缺口和下一步。技术字段只在证据下钻中显示。

### 4.2 经营事实与业务假设分开

调用、Token、估算模型成本、成功率、时延、缓存、运行、分析和产物属于平台事实。节省工时、小时价值、避免损失和新增收益属于业务假设或业务结果，必须显示其来源和验证状态。

### 4.3 图表必须帮助决策

每个 BI 图表必须回答一个明确问题。页面不增加仅用于装饰的饼图、等高柱状图或无法解释的综合分数。

### 4.4 建议可落地但默认不执行

优化建议可以生成结构化整改草案。保存草案、提交审批、候选验证和生产执行保持分离；`DF_FINOPS_ACTIONS_ENABLED` 默认继续关闭。

### 4.5 缓存优先而非刷新优先

用户进入页面时先看到最近成功结果。后台更新不能清空页面，也不能恢复整页骨架。

## 5. 效能与 ROI 页面

### 5.1 经营判断

页面顶部显示一条经营判断，示例：

> 测算显示具备投入价值，业务结果仍需验证。

判断同时展示状态标签：

- `情景测算`；
- `结果待验证`；
- `可复核结果`，仅在成本完整且业务结果已验证时出现。

判断文本由确定性规则根据证据状态生成。Agent 可以解释判断，但不能改变状态。

### 5.2 核心指标

首屏保留四个相同时间口径的经营指标：

- 月度总投入；
- 月度可量化价值；
- 月度净收益；
- 预计回收周期。

每个指标都显示 `observed`、`estimated`、`verified`、`partial` 或 `unavailable`。页面不得混用选定查询窗口成本与月度情景成本，却使用同一个无说明标题。

### 5.3 价值桥接 BI

价值桥接图解释净收益的构成：

1. 节省人工时间价值；
2. 避免损失或新增价值；
3. 实施与运行投入；
4. 月度净收益；
5. 情景 ROI 与预计回收周期。

图表值全部由服务端使用同一 ROI 公式版本计算。前端只格式化和绘制，不重新计算财务结果。

### 5.4 证据成熟度

证据成熟度使用四阶段链路：

`投入 → 使用 → 产出 → 业务结果`

每个阶段返回：

- 数值与单位；
- 证据状态；
- 证据数量；
- 证据缺口；
- 可用的下钻引用。

成熟度百分比必须由明确的阶段权重计算并在接口中返回公式版本；不能由前端主观生成。若产品不需要百分比，则退化为四阶段状态，不显示综合数值。

### 5.5 单位效能趋势

单位效能趋势同时展示：

- 每次成功调用成本或每次分析成本；
- 有效分析或产物数量；
- 对比周期；
- 数据完整状态。

该图用于判断效率变化，不能把调用增长直接解释为价值增长。分母为零时显示不可用，不显示零成本。

### 5.6 能力与口径说明

页面明确区分：

平台自动确认：

- 调用、Token 和模型估算成本；
- 成功率、时延、错误和缓存节省；
- 运行、分析、产物和工作区关联。

业务侧补充与验证：

- 节省工时与小时价值；
- 避免损失或新增收益；
- 结果负责人审核；
- 已实现价值确认。

运营 AI 可以解释指标变化、证据缺口和数字来源，但不能把情景测算升级为已实现 ROI。

## 6. 风险与优化页面

### 6.1 风险判断

页面顶部显示当前主要风险域和建议优先处理数量，例如：

> 风险集中在响应体验与成本效率，建议优先验证 2 项。

风险域固定为：

- 成本；
- 体验；
- 效率；
- 治理。

页面不生成无法解释的单一风险分数。

### 6.2 风险矩阵

风险矩阵使用两个有来源的维度：

- 业务影响；
- 证据置信度。

风险项至少覆盖：

- 预算或成本压力；
- 缓存效率；
- Token 异常增长；
- 响应时延；
- 调用失败率；
- 计价覆盖；
- 统一入口治理覆盖。

图中每个点可选择并联动优先事项、证据和整改方案。客户界面统一使用“统一入口”，不直接展示特定云网关产品名称。

### 6.3 优先事项

每条优先事项显示：

- 标题与业务说明；
- 影响范围；
- 证据置信度；
- 实施难度；
- 预计影响或潜在节省；
- 当前状态；
- 特定证据引用；
- “查看证据”与“查看整改方案”入口。

无法可靠估算节省时显示“待验证”，不得用固定比例生成看似精确的金额。

### 6.4 优化组合 BI

优化组合图使用：

- 纵轴：价值影响；
- 横轴：实施难度；
- 气泡大小：受影响请求、成本或工作区数量；
- 气泡颜色：风险域。

所有轴值和气泡含义必须在接口元数据中返回。该图帮助排序，不代表自动执行顺序。

### 6.5 特定证据处置链

选中风险后展示：

`信号 → 影响范围 → 代表证据 → 建议 → 改善验证`

不同风险必须选择不同证据：

- 时延风险优先选择高时延请求；
- 缓存风险优先选择 `miss` 或 `bypassed` 请求；
- 失败率风险优先选择对应错误类别；
- 计价风险优先选择未映射模型或 deployment；
- Token 风险优先选择异常增长窗口的主要贡献者。

没有直接引用时才按当前范围读取候选请求。不得让所有“查看证据”都落到同一条最近请求。

### 6.6 AI 运营解读

AI 解读嵌入当前风险或当前指标，不再单独占据整块页面。输出回答：

1. 发生了什么；
2. 为什么值得关注；
3. 当前证据支持什么；
4. 哪些结论仍需验证；
5. 下一步如何验证。

分析只使用当前授权范围的聚合事实和证据白名单。自动刷新不触发新分析。

## 7. 结构化整改草案

### 7.1 定位

每条满足证据门槛的优化机会可以生成一个整改草案。草案不是执行命令，也不是生产配置。

草案状态为：

`draft → reviewed → pending_approval → promoted|closed`

只有被提升为现有 typed governance action 后，才进入现有审批、候选执行、验证和回滚状态机。

### 7.2 数据类型

`FinOpsRemediationDraft` 至少包含：

- `draft_id`、`tenant_ref`、`workspace_id`；
- `source_opportunity_id`、`source_anomaly_id`；
- `risk_type`、`title`、`summary`；
- `scope`：工作区、Agent、模型、操作类型；
- `evidence_refs`；
- `proposed_changes`：受枚举约束的修改项；
- `expected_impact`：数值、单位、状态和计算依据；
- `prerequisites`；
- `risks_and_guardrails`；
- `verification_plan`：基线、候选窗口、成功标准和最小样本；
- `rollback_plan`；
- `action_kind`：`cache_policy`、`model_route`、`price_mapping`、`budget_notification` 或 `investigation`；
- `execution_capability`：`advisory_only` 或 `typed_action_available`；
- `base_version`；
- `status`、`created_by`、`reviewed_by`、时间戳和 revision。

`proposed_changes` 不接受任意脚本、XML、URL 或资源 ID。

### 7.3 生成规则

- 数值、影响范围、样本和证据由服务端确定性生成；
- Agent 只能补充说明、风险和验证建议；
- Agent 引用必须来自本次输入的证据白名单；
- 证据不足时生成 `investigation` 草案，而不是可执行变更；
- 只有支持 typed executor 的草案可以提升为治理动作；
- 保存草案不要求开启生产执行开关；
- 提升、审批和执行继续遵守异人审批与版本漂移检查。

### 7.4 缓存策略整改示例

缓存整改草案可以包含：

- 限定工作区、数据版本、分析模式和模型路由一致时才允许复用；
- 候选有效期；
- 主动绕过条件；
- 结果一致性抽样；
- 命中率、单位成本、成功率和 P95 的验证阈值；
- 原策略版本和回滚方式。

内部缓存键不得返回客户端。

## 8. 公共接口

### 8.1 ROI 决策接口

新增：

`GET /api/finops/roi/decision`

公共查询参数沿用当前 `from/to/workspace_id/department_id/agent_id/actor_ref/model`。响应包含：

- 通用 `scope/window/freshness/coverage/currency/data_status`；
- `decision`；
- `metrics`；
- `value_bridge`；
- `evidence_maturity`；
- `unit_economics_trend`；
- `capability_explanation`；
- `scenarios`；
- `evidence_gaps`。

接口内部可以复用现有 ROI snapshot、cost-value snapshot 和 economics service，但客户端只发起一个首屏请求。

### 8.2 风险决策接口

新增：

`GET /api/finops/risk/decision`

响应包含：

- 通用响应信封；
- `decision`；
- `risk_domains`；
- `risk_matrix`；
- `priorities`；
- `optimization_portfolio`；
- `selected_evidence_summaries`；
- 最新已保存 AI 解读；
- 整改草案摘要；
- 治理能力状态。

接口内部复用现有 anomaly、recommendation、opportunity、insight 和 action service。自动读取接口不得触发 Agent。

### 8.3 整改草案接口

新增：

- `GET /api/finops/remediation-drafts`
- `POST /api/finops/remediation-drafts`
- `GET /api/finops/remediation-drafts/{draft_id}`
- `POST /api/finops/remediation-drafts/{draft_id}/review`
- `POST /api/finops/remediation-drafts/{draft_id}/promote`
- `POST /api/finops/remediation-drafts/{draft_id}/close`

创建接口接受 `source_opportunity_id`、允许的目标范围和 `base_version`，不接受完整任意方案正文。服务端根据最新证据生成标准字段。

提升接口只对 `typed_action_available` 草案生效，并创建现有 `FinOpsAction`。`investigation` 草案只能复核和关闭。

## 9. 缓存与加载数据流

### 9.1 浏览器缓存

新增统一的页签级 `FinOpsDataStore`，缓存键包含：

- tenant 和身份权限摘要；
- workspace；
- 时间窗口；
- 部门、Agent、人员和模型筛选；
- 页签；
- 接口 schema revision。

状态规则：

- 5 分钟内为 `fresh`；
- 5 至 30 分钟为 `stale_usable`；
- 超过 30 分钟为 `expired`；
- `fresh` 直接使用且不发请求；
- `stale_usable` 先展示，再静默更新；
- `expired` 或无缓存才显示局部骨架。

缓存只保存在当前应用会话内，不把运营数据写入 `localStorage`。跨设备复用由服务端 Redis 和 SQL 聚合承担。

### 9.2 预加载

- 登录和工作区授权完成后，在浏览器空闲时预加载默认范围 bootstrap；
- 进入运营管理后立即消费缓存，不再 `force` 重新请求；
- 首屏稳定后空闲预取当前最可能访问的 ROI 或风险决策接口；
- hover、focus、touch 和空闲预加载共享同一个在途请求；
- 权限、workspace 或筛选范围变化时取消旧请求并隔离缓存。

### 9.3 自动刷新

- 默认每 10 分钟静默更新；
- 页面不可见时暂停；
- 恢复可见时，仅在当前数据超过 10 分钟时更新；
- 只更新当前页签和当前范围；
- 非活动页签不参与定时刷新；
- 自动刷新不越过可用客户端缓存，不触发 Agent；
- 顶部显示“最近更新于 …”，更新中只显示轻量状态，不移动布局。

### 9.4 手动刷新

手动刷新才强制重新验证当前页签。强制刷新不等于绕过授权、数据状态或服务端保护。

### 9.5 服务端缓存

Redis 为聚合响应保留：

- 5 分钟 fresh 窗口；
- 30 分钟 stale 可用窗口；
- `generated_at`、`fresh_until`、`stale_until` 和 cache status。

当 fresh 过期但 stale 可用时，API 可以返回旧聚合并触发一次受控刷新。同一缓存键只允许一个重算任务，避免并发缓存穿透。

缓存键继续包含 tenant、授权 workspace、查询范围和操作类型。不得跨租户或跨权限摘要复用。

### 9.6 SQL 聚合

Dashboard 优先读取小时或日 rollup。请求级账本仅用于：

- 证据下钻；
- rollup 重算；
- 当前窗口尚未进入 rollup 的增量合并。

聚合任务保持幂等。迟到事件按事件 ID 和发生时间重新归并，不能重复计数。

### 9.7 局部失效

写操作使用 workspace 与数据域 revision 失效缓存：

- ROI 情景或结果验证：失效 ROI 与相关总览摘要；
- 异常确认或抑制：失效风险；
- 整改草案：失效风险与草案列表；
- 价目表变更：失效成本、ROI 和依赖成本的风险；
- 模型路由或缓存策略变更：失效风险、成本、ROI 和相关运行摘要；
- 与当前运营数据无关的设置不失效 Portal 缓存。

不扫描或删除 Redis 的宽泛键空间。

## 10. 错误与状态处理

- 有最近成功结果时，更新失败继续展示旧数据；
- 显示“更新失败，当前展示 N 分钟前的数据”和重试入口；
- 只有首次进入且没有任何可用缓存时显示局部错误；
- ROI 页的某个图表不可用时，不清空其他模块；
- 风险页的 AI 解读不可用时，规则、机会、证据和整改草案仍可使用；
- Redis 不可用时回退到 SQL 或现有 query service，并返回 `cache_status=unavailable`；
- SQL 聚合不可用时返回 `partial` 或 `unavailable`，不得制造零值；
- 保存整改草案发生 `base_version` 冲突时返回 409，客户端重载最新方案并要求重新复核。

## 11. 前端组件边界

避免继续扩大 `FinOpsPortal.jsx`。实现应拆分为：

- `RoiDecisionPage`：经营判断、价值桥接、证据成熟度和单位效能；
- `RiskDecisionPage`：风险判断、矩阵、优先事项和优化组合；
- `RemediationDraftPanel`：结构化草案浏览、生成和状态；
- `FinOpsCapabilityNote`：口径与能力说明；
- `FinOpsDataStore`：缓存、在途请求合并、刷新和局部失效；
- 独立的 ROI、风险和整改 view model；
- 共享 BI 图表基础组件，负责可访问性、tooltip、空值和响应式布局。

业务计算留在服务端或纯 view model，React 组件不自行推断 ROI、节省或风险等级。

## 12. 隐私、安全与客户表达

- 继续从可信 Easy Auth 声明推导 tenant 和权限；
- member 不得读取未授权 workspace、组织级人员明细或管理员整改草案；
- 客户界面使用“统一入口”“运行追踪”等产品化名称；
- 云服务名称只在受控技术详情、配置页或外部监控深链中出现；
- 证据抽屉只展示允许的业务请求摘要和最终可见回答摘要；
- 技术 ID 保持折叠；
- 整改草案不得包含密钥、原始身份、缓存键、任意 URL、脚本或内部错误正文；
- 演示工作区可以保存丰富且一致的数据，但客户界面不显示“演示数据”标签；其内部 provenance 仍需保留。

## 13. 测试与验收

### 13.1 Python

- ROI 决策响应保持情景、观测和验证状态分离；
- 价值桥接使用同一公式 revision；
- 证据成熟度和证据缺口可复现；
- 风险矩阵、优先级和优化组合由输入事实确定；
- 不同风险选择不同证据；
- 预计节省在价格或样本不足时返回不可用；
- 整改草案创建、revision、review、promote 和 close；
- advisory 草案不能提升为 typed action；
- typed 草案提升后仍遵守审批人与提出人分离；
- Redis fresh、stale、single-flight、失效和不可用回退；
- 跨租户、跨 workspace 和跨权限缓存隔离；
- additive SQL migration 幂等。

### 13.2 Node

- ROI 和风险 view model 不补造未知值；
- BI 比例与坐标使用真实数据差异；
- 单位为零、负值、空值和 partial 状态正确；
- 浏览器缓存 fresh/stale/expired 行为；
- 相同在途请求合并；
- 写操作只失效对应域；
- 更新失败保留最近成功数据；
- 指标 tooltip、键盘焦点和 reduced motion。

### 13.3 Playwright

- 暖缓存进入运营管理不显示整页骨架；
- 5 分钟内多次切换 ROI 与风险页签不重复请求；
- 10 分钟静默刷新只请求当前可见页签；
- 页面隐藏时不刷新；
- 手动刷新强制重新验证；
- ROI 价值桥接、证据成熟度和能力说明桌面与移动端可读；
- 风险矩阵联动不同优先项和不同证据；
- 从优化机会生成整改草案；
- 保存草案不触发生产动作；
- stale 数据更新失败时页面保持可用；
- member 权限和管理员整改权限正确。

### 13.4 性能目标

- 暖缓存进入运营管理目标在 300 ms 内形成可交互首屏；
- 5 分钟内重复切换同一页签不产生网络请求；
- 后台刷新期间不恢复整页骨架；
- ROI 和风险首屏各使用一个聚合请求；
- 相同范围的并发聚合请求只触发一次服务端重算；
- 记录冷缓存、Redis hit、Redis stale 和浏览器缓存四种路径的耗时证据。

### 13.5 视觉验收

- 桌面端与移动端截图；
- 页面顶部经营判断不因更新状态改变高度；
- 图表 tooltip 可通过 hover、focus 和 tap 使用；
- BI 图表数值具有真实比例差异；
- 风险和整改信息在 1366px 宽度下不被抽屉覆盖；
- 无永久装饰点、错位问号、边框覆盖或居中文字漂移。

## 14. 发布边界

- SQL 仅使用 additive migration；
- 先部署零流量 backend 和 web candidate；
- 保持 `DF_FINOPS_ACTIONS_ENABLED=0`；
- 完成登录态桌面、移动端、缓存命中、失效、不同证据和整改草案验收；
- candidate 健康且回归通过后，再申请流量切换；
- 本设计与后续实现计划均不构成生产切流授权。

## 15. 最终成功标准

一次宣讲中，用户可以沿同一产品路径完成：

1. 在 ROI 页理解当前投入、情景价值、证据成熟度和口径；
2. 在风险页识别最重要的成本、体验或治理问题；
3. 从风险进入与该风险匹配的请求和趋势证据；
4. 查看具体修改范围、预期改善、验证标准和回滚方案；
5. 保存整改草案而不直接执行生产变更；
6. 返回页面或切换页签时立即看到最近结果，不再反复等待整页刷新。
