# DeepSeek 接入与运营 AI 双速优化设计

日期：2026-08-08
状态：已确认设计，待实施计划
范围：DataForge 新生产环境、模型提供商管理、运营 AI 会话与候选运行路由

## 1. 背景与已验证现状

本设计处理两个彼此关联但边界独立的问题：DeepSeek 原厂连接无法恢复，以及运营 AI 首次历史加载和生成回复过慢。

当前生产复现得到以下证据：

- DeepSeek 提供商记录已存在于配置数据库，但目标 Key Vault 中没有对应模型提供商 Secret。页面因此仍显示“凭据已安全保存”，实际连接检测无法读取凭据。
- 后端托管身份在目标 Key Vault 上只有 Secret 读取权限，没有写入权限，因此重新录入或轮换 Key 也无法完成持久化。
- 模型提供商配置入口已开启，但外部模型运行路由与自动网关配置仍关闭。
- `deepseek-v4-flash` 是当前官方有效模型标识，模型名不是本次失败原因。
- DeepSeek 连接检测实测约 23 秒后返回泛化失败信息，没有向用户指出失败层级。
- 运营 AI 首次打开时，历史同步实测约 27 秒；同一页面再次打开可命中前端内存缓存。
- 运营 AI 一次结构化回答实测约 55 秒。当前链路串行读取会话、重新聚合完整运营上下文，并以全分析路径调用 Terra，前端只能等待完整响应。

这些数字用于定位本次环境与链路问题，不作为所有区域和模型负载下的固定承诺。

## 2. 目标

### 2.1 DeepSeek

- 修通 Key 的写入、读取、轮换、连接检测和可用模型发现。
- 让界面准确区分“记录存在”和“凭据实际存在”。
- 连接通过后允许 DeepSeek 进入候选 Agent 路由，并保留 Azure 模型自动兜底。
- 候选验收通过前不启用生产外部模型运行开关。
- 全链路保持 Key 只写、不回显，不在日志、数据库业务表、API 响应或 Git 中保存明文。

### 2.2 运营 AI

- 页面进入后立即预加载会话历史，打开助手时优先展示本地快照。
- 将首次历史冷加载目标控制在 5 秒内，温缓存打开目标控制在 1 秒内。
- 提供双速模式：普通问答走快速模型，主动深度分析走 Terra。
- 快速回答目标为 5–12 秒，连续实测的 P95 验收门禁为 20 秒。
- 深度分析在 1 秒内返回真实进度，目标在 45 秒内完成。
- 保留结论、依据、影响、建议、判断边界和请求级证据约束。

## 3. 非目标

- 不复制或迁回已经删除的旧订阅资源。
- 不恢复旧 Key 明文；目标环境必须由用户重新录入有效 Key。
- 不绕过 APIM、租户隔离、工作区授权或审计边界。
- 不在本轮引入自动生产治理动作。
- 不把运营 AI 改造成开放式通用聊天机器人。
- 不承诺外部模型在所有时段达到固定延迟；验收以候选环境连续样本为准。

## 4. 总体方案

采用“真实链路修复 + 双速问答”的分层方案，不使用单纯延长超时或只增加加载动画的方式掩盖问题。

```text
模型提供商设置
  -> 安全配置校验
  -> Key Vault 凭据写入/读取
  -> DNS/TLS 探测
  -> 原厂认证与最小模型调用
  -> 模型发现与计价关联
  -> 候选 APIM 路由
  -> Azure 自动兜底

运营页面进入
  -> 历史 bootstrap 预取
  -> 浏览器内存快照先显示
  -> Redis 短期会话快照静默刷新
  -> 用户选择快速问答或深度分析
  -> 服务端复用运营指标快照
  -> 返回真实阶段事件与最终结构化回答
  -> SQL 持久化跨设备历史
```

## 5. DeepSeek 连接设计

### 5.1 凭据权限与状态校准

后端托管身份在目标 Key Vault 范围获得 `Key Vault Secrets Officer`，不授予订阅或资源组范围权限。API 仍只暴露受审计的创建与轮换操作，不提供任意 Secret 名称、读取或删除接口。

提供商读取响应新增安全凭据状态：

- `stored`：Secret 引用和 Secret 实体同时存在。
- `missing`：数据库记录存在，但目标 Vault 中没有实体。
- `unavailable`：无法安全确认，不能声称已保存。

前端只有在 `stored` 时显示“凭据已安全保存”。`missing` 显示“需要重新录入 Key”。

### 5.2 分阶段连接检测

连接检测分为以下阶段，每个阶段记录安全类别与耗时，不记录 Key、原厂响应正文或解析失败正文：

1. `secret_read`：读取并校验目标 Secret。
2. `endpoint_resolution`：校验官方 HTTPS 主机及 DNS 解析。
3. `tls_connect`：建立 TLS 连接。
4. `provider_auth`：执行受限认证请求。
5. `minimal_inference`：使用当前官方快速模型、显式非思考模式执行最小非业务调用。
6. `model_discovery`：依据官方受控模型目录确认并写入允许进入候选范围的模型清单。

连接和读取使用独立短超时。网络类失败允许一次有界重试；认证失败、余额不足、参数错误和缺失凭据不重试。

### 5.3 安全错误分类

服务端返回受控分类，前端映射为可操作文案：

| 安全分类 | 用户文案 | 是否重试 |
| --- | --- | --- |
| `provider_secret_missing` | 需要重新录入 Key | 否 |
| `provider_secret_write_denied` | 安全凭据无法保存 | 否 |
| `authentication_failed` | 身份认证失败，请更新 Key | 否 |
| `insufficient_balance` | 原厂账户余额不足 | 否 |
| `provider_endpoint_dns_unavailable` | 原厂地址暂时无法解析 | 是，一次 |
| `provider_tls_unavailable` | 无法建立安全连接 | 是，一次 |
| `provider_timeout` | 原厂服务响应超时 | 是，一次 |
| `rate_limited` | 请求过于频繁，请稍后重试 | 是，一次 |
| `provider_unavailable` | 原厂服务暂时不可用 | 是，一次 |

原始异常只进入受控内部诊断；公共 API 和界面不得返回原厂错误正文。

### 5.4 候选运行与兜底

连接成功、模型受支持且价格已关联后，DeepSeek 才进入候选 Agent 模型选择。实际生产运行需要独立的外部路由开关。

外部运行通过现有受治理网关路径，记录安全 Provider、模型、Token、延迟、缓存和估算成本元数据。候选环境只允许 typed DeepSeek 网关适配器生成候选 revision，不接受用户提供的 APIM XML、脚本或任意资源 ID。仅在尚未输出内容且没有副作用时，网络超时、限流和原厂 5xx 可自动切换到已配置 Azure 备用模型；认证失败、余额不足和参数错误不进行静默兜底，避免掩盖配置问题。

## 6. 运营 AI 双速设计

### 6.1 历史 bootstrap

新增一次性只读 bootstrap 接口，服务端在一次授权和一次数据库往返中返回：

- 最近有效会话引用；
- 最近有限数量的用户与助手消息；
- 会话更新时间、到期时间和数据状态。

SQL 查询使用现有 tenant、actor、workspace 复合范围和消息顺序索引。接口不返回其他成员会话。

前端在工作区范围确认后立即预取，不等待用户点击 AI：

- 有内存快照时立即显示，再进行静默校准。
- 没有快照时显示紧凑历史骨架，不阻塞页面其他内容。
- 修正“存在缓存时反而强制刷新”的行为。
- 同一工作区合并并发请求，切换工作区时取消过期请求。

### 6.2 两级缓存

- 浏览器内存缓存用于即时展示，默认保留 5 分钟。
- Redis 保存短期会话 bootstrap 快照，并使用 tenant、actor、workspace 作为完整命名空间。
- SQL 仍是跨设备历史的最终来源。
- 追加消息、清空历史、会话过期和工作区切换时，使对应缓存失效。
- 缓存故障不得阻塞 SQL 回退；失败结果不进入缓存。

### 6.3 运营指标快照复用

助手不再为每次问题重新构建完整的 31 天趋势、部门分解、工作区分解和请求集合。服务端从可信查询服务读取与当前页面相同的缓存快照，并只构建：

- 当前指标与单位；
- 当前筛选范围和时间窗口；
- 当前指标必要的聚合摘要；
- 最多三条请求级证据及友好名称；
- 匹配的定义、公式和判断边界；
- 最近六轮、每轮有界长度的会话历史。

客户端传入的指标值只作为请求意图，最终数值和证据仍由服务端授权范围内的数据生成。

### 6.4 双速模型路由

模型设置增加两个独立、带版本校验和审计的配置：

- “运营 AI 快速回答模型”：默认选择允许列表中的 Luna 或 GPT-5.1。
- “运营 AI 深度分析模型”：默认选择 Terra。

普通输入和指标卡“问 AI”使用快速路径，输出上限保持紧凑。界面提供明确的“深度分析”操作，只有用户主动选择时才使用 Terra 与更完整上下文。DeepSeek 完成连接、治理和计价后可以被管理员分配给任一路径。

两种路径使用同一公共回答契约，避免模型切换改变前端展示结构。

### 6.5 真实进度流

新增 `application/x-ndjson` 流式查询接口，按顺序发送受控事件：

- `evidence_loading`
- `context_ready`
- `model_processing`
- `answer_validating`
- `completed` 或 `failed`

事件不包含原始请求正文、原始身份、Key 或原厂响应。最终 `completed` 事件携带现有结构化回答契约。前端只展示已经由服务端发出的真实阶段，不使用定时器伪造进度。

网络中断时允许用户重试同一问题；服务端使用请求引用避免重复持久化同一轮消息。

## 7. API 与数据契约

### 7.1 Provider

现有提供商接口保持兼容，公共 Provider 响应补充：

- `secret_status`
- `connection_stage`
- `stage_durations_ms`
- `safe_error_category`

`stage_durations_ms` 只包含阶段耗时，不包含地址、Key、响应正文或内部资源标识。

### 7.2 Assistant

新增：

- `GET /api/finops/assistant/bootstrap?workspace_id=...`
- `POST /api/finops/assistant/query/stream`

流式请求在现有 `AssistantRequest` 基础上增加 `mode=quick|deep` 和幂等 `request_ref`。非流式 `/assistant/query` 暂时保留，用于兼容现有客户端与回退。

所有接口继续从可信 Easy Auth 声明推导 tenant 和 actor，并在服务端收窄 workspace。

## 8. 前端体验

### 8.1 运营页面比例基线

主视觉验收以用户当前桌面截图的 `3056×1656` 物理像素显示环境为基准。实施时读取浏览器 CSS viewport，不将物理像素直接作为 CSS 尺寸，也不依赖浏览器缩放来修正布局。

- 主内容阅读宽度稳定在 `1440–1500px`，在用户宽屏上居中并保留自然留白，避免面板随屏幕无限拉宽。
- 页面使用 12 栏语义栅格和 `14px` 主间距；主要分析区使用 8 栏，辅助判断区使用 4 栏，只有趋势和请求证据等必要内容占满整行。
- 普通卡片统一约 `10px` 圆角、`18px` 内边距和轻量边框；避免卡片内部继续堆叠同等级卡片和粗重阴影。
- KPI 卡保持 `136–148px` 的稳定高度，常规图表保持约 `280–300px`，不因宽屏被拉成扁长条。
- ROI 价值桥改为具有明确基准、结果和共同尺度的比例表达，不再使用缺少左右含义的中线长条。
- 成本、ROI、风险证据、优化组合和运营 AI 采用同一套标题层级、状态标签、圆角与留白规则。
- 桌面主验收使用用户当前显示环境截图；同时保留 `1440px`、`1024px` 和 `390px` CSS viewport 的回归，确保 Tooltip、证据抽屉和 AI 浮窗不裁切或遮挡。

### 8.2 交互与状态

- DeepSeek 卡片同时展示连接状态、凭据状态和最近检测阶段，避免把三者压成一个“异常”。
- 缺失凭据时主操作变为“重新录入 Key”，连接检测按钮禁用并说明原因。
- AI 打开后先显示缓存历史；后台同步时显示不遮挡消息的轻量状态。
- 快速和深度模式使用清晰标签，深度模式说明“耗时更长，使用 Terra 进行完整分析”。
- 回答继续使用小标题和分段，不展示 JSON、验证异常或原始证据编号。
- 模型失败时保留用户问题和重试入口，不用通用大段错误覆盖历史。

## 9. 测试与验收

### 9.1 自动化测试

- Secret 缺失、无写权限、无效 Key、余额不足、DNS/TLS、超时和限流分类测试。
- Provider 公共响应不得出现 Key、Secret 值、原厂响应正文或原始异常。
- DeepSeek 成功连接、模型发现、候选选择和 Azure 有界兜底测试。
- bootstrap 单次查询、缓存命中、TTL、租户/成员/工作区隔离、失效和 SQL 回退测试。
- 运营快照复用、紧凑上下文、最多三条证据和服务端数值权威性测试。
- quick/deep 路由选择、版本冲突和审计测试。
- 流式阶段顺序、中断、幂等重试与失败终态测试。
- Playwright 覆盖桌面和移动端的凭据修复、历史即时展示、快速问答、深度进度和模型失败体验。

### 9.2 候选实测

- 使用用户重新录入的有效 Key 完成一次连接检测和模型发现。
- 完成一次 DeepSeek 候选调用，并验证 Token、模型和估算成本进入对应统计。
- 制造一次可重试外部失败，确认在无输出、无副作用条件下切换到 Azure 备用模型。
- 对同一工作区连续三次冷/温历史打开采样。
- 对快速回答连续采样，目标 5–12 秒，P95 不超过 20 秒。
- 深度分析在 1 秒内出现服务端阶段事件，目标 45 秒内完成。
- 跨工作区、跨成员访问不得复用历史或运营快照。
- Python、Node、Vite、Playwright 全量回归和 `git diff --check` 通过。
- 扫描提交、镜像构建输入和 Git 历史，不得出现 Key、Token、PAT、生产响应或测试产物。

## 10. 部署与回滚

1. 先部署零流量候选后端和前端。
2. 在目标 Key Vault 范围为后端身份补充 Secret 写入权限。
3. 用户在候选页面重新录入 DeepSeek Key；实施人员不读取或转存 Key。
4. 运行连接、快速问答、深度分析、兜底和跨租户验收。
5. 切换应用版本时继续保持生产外部运行开关关闭。
6. 获得单独批准后启用外部模型生产运行，并保留 Azure 备用路由。
7. 若候选或生产验收失败，关闭外部运行开关并回退应用 revision；保留 Provider 配置记录和安全错误证据，不回显或导出 Key。

生产外部路由的启用是独立门禁，不因代码部署或连接成功而自动发生。

## 11. 实施边界

本轮允许修改 Provider 连接服务、Key Vault 权限、模型策略、运营 AI API、缓存和前端交互；不修改 Easy Auth 信任模型，不开启 FinOps 自动治理执行，不删除用户工作区数据，也不清理当前工作树中的既有验收产物。
