# DataForge 成本治理、风险扫描与上下文 AI 设计

日期：2026-08-03
状态：方案 B 已确认，待实施计划

## 1. 背景与问题

DataForge 的运营管理已经具备成本、效能、ROI、异常、请求证据和运营 AI，但当前体验没有形成可讲清楚的 IT 运营闭环：

- 左侧只有“运营管理”一个入口，成本、ROI 与风险挤在同一组页签里；
- 部分“查看证据”按钮只传显示原因，没有传具体请求引用，最终统一回退到最近请求；
- 风险页虽然按规则计算异常，但没有展示本次检查范围、规则版本、阈值、样本和扫描时间；
- “问 AI”只打开浮层，不会根据点击位置自动生成并发送问题；
- AI 回答当前是单段字符串，服务端会压平换行，前端也没有稳定的小标题和列表结构；
- AI 回答中的“查看证据”没有继续传递本次回答引用的证据；
- 演示工作区已经有缓存、慢请求、失败、未计价、Token 异常和统一入口覆盖等不同场景，但产品界面没有把这些场景逐项绑定到对应指标。

本设计将运营能力组织为：

`运营监控 → 规则扫描 → 风险判定 → 对应证据 → AI 解读 → 优化建议`

规则负责判断，证据负责复核，AI 负责解释。三者不得混为一体。

## 2. 目标

### 2.1 产品目标

- 面向 IT、平台运营和财务人员建立简洁、可解释的成本治理中心；
- 将“风险与优化”从成本页签中独立为左侧一级业务入口；
- 每个指标、风险项、ROI 阶段和 AI 回答都只能打开自身关联的证据；
- 提供用户可主动执行的只读风险扫描，并展示判定依据；
- 点击局部“问 AI”后自动带入上下文、生成问题并发起咨询；
- AI 回答以稳定的小标题、段落和列表呈现；
- 演示工作区具备完整且有区分度的展示内容，非演示工作区不补造数据。

### 2.2 技术目标

- 复用现有 FinOps request ledger、价目表、异常规则、缓存、ROI、证据别名和授权边界；
- 使用 additive SQL 保存风险扫描元数据和扫描结果快照；
- 使用统一的证据集合投影，消除字符串原因触发的“最近请求”兜底；
- 扩展运营 AI 的结构化响应，同时兼容历史纯文本会话；
- 扫描不依赖分析 Agent，自动刷新也不触发扫描或 AI；
- 保持 `DF_FINOPS_ACTIONS_ENABLED=0`，不扩大为自动生产治理。

## 3. 非目标

- 不接入 Azure 实际账单或 Cost Management 对账；
- 不扫描客户云资源、网络、主机或数据库；
- 不自动修改模型路由、缓存、预算、价目表或统一入口策略；
- 不允许 Agent 批准、执行或回滚治理动作；
- 不采集完整 prompt、provider 原始响应、密钥、原始身份或内部错误正文；
- 不在非演示工作区制造固定风险、固定收益或固定请求；
- 不把每次页面刷新包装成一次新的风险扫描；
- 不增加第二个 AI 抽屉、底部咨询横幅或永久右侧面板。

## 4. 信息架构

左侧导航保持三个主分组，运营分组调整为：

- 业务工作台
- 运营治理
  - 成本管理
  - 风险与优化
- 系统

### 4.1 成本管理

“成本管理”使用现有运营 Portal 外壳，内部只保留：

- 运营总览；
- 成本分析；
- 效能与 ROI。

运营总览继续承担成本、调用质量、缓存收益、价值状态和需要关注事项的单屏判断。风险详情不再作为该页面的第四个页签。

### 4.2 风险与优化

“风险与优化”成为独立左侧入口，与“成本管理”共享：

- tenant 与 workspace 授权；
- 日期、部门、Agent 和模型筛选；
- 缓存优先数据层；
- 证据抽屉；
- 浮动运营 AI；
- 统一视觉与响应式组件。

导航采用两个稳定 view id：`finops` 和 `finops-risk`。旧的 `finops?tab=risk` 或历史内部状态继续归一到 `finops-risk`，避免旧入口失效。

## 5. 只读风险扫描

### 5.1 用户语义

页面主操作命名为“运行风险扫描”。辅助说明固定为：

> 根据当前范围的调用、成本、缓存、时延、错误、计价与统一入口证据执行只读检查，不会修改生产配置。

扫描不是云资源扫描，也不是 Agent 自主巡检。它是在当前授权数据范围内重新执行服务端确定性规则。

### 5.2 扫描流程

1. 服务端从可信身份推导 tenant，并收窄 workspace；
2. 固化当前查询窗口、筛选条件、ledger freshness 和策略 revision；
3. 加载当前范围内的规范请求事实与所需聚合；
4. 执行允许的规则集合；
5. 为每条命中规则选择与该规则语义匹配的请求证据；
6. 保存扫描元数据、规则结果和证据引用；
7. 失效当前 workspace 的风险查询缓存；
8. 返回扫描摘要和最新风险决策投影。

扫描不自动调用 AI。用户点击风险项“问 AI”时才生成解释。

### 5.3 默认规则

沿用现有规则及管理员配置：

- 调用失败率；
- P95 响应时延；
- 日预算使用；
- Token 异常增长；
- 统一入口覆盖；
- 未计价调用；
- 缓存命中率。

每条规则结果必须返回：

- `policy_type` 与客户友好名称；
- `rule_revision`；
- `status`：`triggered|clear|insufficient_data|unavailable`；
- 观测值、阈值、单位；
- 样本数量与最小样本要求；
- 查询窗口和筛选范围；
- 严重度与影响域；
- 判定说明；
- 特定证据引用；
- 建议和需要验证的缺口。

样本不足必须显示“样本不足”，不得生成风险。

### 5.4 扫描状态

扫描状态为：

`running → completed|failed`

扫描失败不得清空上一份成功结果。页面继续显示上一次扫描，并提示本次扫描失败。

### 5.5 数据类型

`FinOpsRiskScan` 至少包含：

- `scan_ref`：安全不透明标识；
- `tenant_ref`、`workspace_id`；
- `window` 与受控筛选条件；
- `status`；
- `policy_revision`、`ledger_revision`；
- `rules_evaluated`、`rules_triggered`、`rules_clear`、`rules_insufficient`；
- `request_sample_count`、`evidence_coverage_pct`；
- `started_at`、`finished_at`；
- `initiated_by_ref`，仅服务端使用；
- `findings`，保存受控规则结果与请求引用；
- `error_category`，不保存内部错误正文。

SQL 使用 additive 表 `df_finops.risk_scans` 与 `df_finops.risk_scan_findings`。扫描事实默认保留 90 天。

### 5.6 接口

- `POST /api/finops/risk/scans`
- `GET /api/finops/risk/scans/latest`
- `GET /api/finops/risk/scans/{scan_ref}`

创建接口只接受 `workspace_id/from/to/department_id/agent_id/model` 等现有受控范围字段，不接受自定义规则、脚本、XML、查询文本或资源 ID。

只有 workspace owner/admin 可以发起扫描和读取完整扫描详情。已有风险读权限的成员只能读取其授权范围内的安全摘要。

## 6. 风险页面布局

### 6.1 首屏结构

桌面首屏顺序为：

1. 页面标题与“运行风险扫描”；
2. 扫描状态带；
3. 四个风险域摘要；
4. 风险矩阵与优先事项；
5. 当前选中风险的判定依据与证据入口。

扫描状态带展示：

- 最近扫描时间；
- 当前范围；
- 检查规则数；
- 请求样本数；
- 发现数量；
- 证据覆盖率；
- 策略版本；
- “查看判定依据”。

### 6.2 判定依据

选中风险后显示：

`信号 → 阈值 → 样本 → 影响范围 → 代表证据 → 建议 → 改善验证`

不显示无法解释的综合风险分。AI 解读不能覆盖或修改规则的观测值、阈值、严重度和状态。

### 6.3 页面下半部分

保留优化组合图和整改草案入口，但压缩为辅助区域。整改草案仍是建议，不是执行命令。

## 7. 逐项证据集合

### 7.1 统一数据结构

新增响应投影 `FinOpsEvidenceSet`：

- `subject_type`：`metric|risk|roi_stage|assistant_answer`；
- `subject_id`；
- `reason`；
- `metric_id` 或 `policy_type`；
- `items`，最多 3 条代表请求；
- `data_status` 与 `evidence_state`。

每个 item 至少包含：

- `request_ref`；
- 客户友好请求名称；
- 发生时间和操作名称；
- 与当前证据点相关的 `signal.metric/value/unit`；
- 状态、错误分类、模型、时延、缓存、Token 和估算成本的安全摘要；
- 可见回答摘要状态；
- 技术信息只保留允许折叠显示的关联键。

### 7.2 选择规则

- 成本：选择当前范围内估算成本最高且已计价的请求；
- 调用质量：选择失败请求及有代表性的成功请求；
- 缓存：选择 `miss`、`bypassed` 和可用的 `hit` 对照；
- Token：选择异常窗口 Token 贡献最高的请求；
- 时延：选择时延最高的请求；
- 未计价：只选择没有可靠价格映射的请求；
- 统一入口覆盖：只选择未关联统一入口或覆盖状态未知的请求；
- ROI 阶段：只选择该阶段已有的运行、请求或业务结果引用；
- AI 回答：只选择模型实际引用且已通过白名单校验的证据。

同一请求可以同时支持两个确实相关的判断，但每个按钮必须拥有自己的有序证据集合和相关信号，不能共享一个无语义的“最近请求”集合。

### 7.3 前端交互

所有 `onEvidence` 调用统一接受对象：

```text
{ reason, subjectType, subjectId, metricId, policyType, evidenceRefs }
```

证据按钮不得只传字符串。只有没有明确证据语义的页面级通用入口允许读取最近请求，并且必须显示“当前范围最近请求”，不能伪装成某个指标的证据。

证据抽屉展示 1–3 条可切换证据，默认打开集合中的第一条。切换请求时复用详情缓存并保留抽屉位置。

## 8. 上下文 AI 自动咨询

### 8.1 点击行为

局部“问 AI”执行以下操作：

1. 生成受控上下文；
2. 根据指标或风险类型生成默认咨询问题；
3. 打开现有浮动运营 AI；
4. 立即把问题显示为用户消息并自动发送；
5. 使用唯一 `interaction_ref` 保证一次点击只发送一次；
6. 不等待远端历史同步完成才显示当前问题。

浮动“运营 AI”启动器仍只打开通用聊天，不自动发问。

### 8.2 默认问题

默认问题由确定性模板生成，不额外调用模型：

- 成本：“当前成本主要由哪些 Agent 和模型贡献，变化是否需要关注？”
- 调用质量：“当前失败和成功情况说明了什么，主要影响来自哪里？”
- 缓存：“为什么缓存命中率处于当前水平，哪些调用最值得优先优化？”
- Token：“Token 用量变化主要由什么造成，是否存在异常上下文或重试？”
- ROI：“当前价值判断中哪些是已观测事实，哪些仍属于估算或待验证结果？”
- 风险：“为什么该风险被判定为当前级别，使用了哪些阈值、样本和证据？”
- 优化建议：“在不自动执行生产变更的前提下，下一步应如何验证这项优化？”

问题连同当前时间窗口、筛选、指标值、规则结果和特定证据引用发送给服务端。

### 8.3 历史与加载

- 登录和 workspace 授权完成后空闲预取 AI 历史；
- 打开浮层先使用内存缓存，历史同步不阻塞当前咨询；
- 远端历史返回时不得覆盖用户刚发送的问题和正在生成的回答；
- 当前工作区的会话继续服务端保留 30 天并支持跨设备；
- 切换 workspace 时严格隔离历史和在途请求。

## 9. 结构化 AI 回复

### 9.1 响应结构

在兼容现有 `answer` 文本的同时，新增结构化展示字段：

- `headline`；
- `summary`；
- `sections`，类型限定为：
  - `finding`；
  - `basis`；
  - `impact`；
  - `recommendation`；
  - `caveat`；
- 每个 section 包含 `heading` 与 1–5 条 `points`；
- `evidence_refs` 与客户友好 `evidence_labels`；
- `suggested_questions`。

模型使用结构化输出 schema。前端按组件渲染小标题、摘要和列表，不直接渲染任意 HTML，也不依赖 Markdown 才能形成排版。

### 9.2 回答原则

- 第一段先给结论；
- 判断依据必须引用当前允许的指标和证据；
- 明确区分观测、估算、部分可用和不可用；
- 建议使用可验证动作，不使用“建议持续关注”作为唯一结论；
- 不输出原始请求 ID、身份、密钥、内部错误正文或隐藏提示；
- 不批准或执行治理动作；
- 证据不足时明确说明缺口，不补造根因。

### 9.3 兼容性

历史纯文本回答继续显示为一个“分析结论”区块。新回答同时保存安全纯文本投影和结构化 sections；历史上下文继续使用受控纯文本，避免把 UI 标记传给模型。

AI 回答中的“查看证据”必须传递该回答的 `evidence_refs`，不得再传纯字符串原因。

## 10. 演示工作区内容

只在 `demo-corpus` 维护可复现的场景集合：

- 高成本已计价请求；
- 高 Token 长上下文请求；
- 缓存 miss、hit 和 bypass 对照；
- 高时延请求；
- provider 失败请求；
- 未计价模型请求；
- 未关联统一入口请求；
- 正常成功请求；
- ROI 使用、产出和待验证业务结果；
- 一份已完成的初始风险扫描。

每个场景的请求摘要、最终可见回答、模型、Token、时延、缓存、成本和状态必须内部一致。页面不显示“演示数据”标签，但内部保留 seed batch 和 provenance，便于幂等更新和清理。

非演示工作区只使用实际观测数据；数据不足时返回 `insufficient_data` 或 `unavailable`。

## 11. 缓存与刷新

- 成本管理和风险页面继续使用 5 分钟 fresh、30 分钟 stale 可用的缓存策略；
- 默认 10 分钟静默刷新，不缩短刷新周期；
- 自动刷新只读取最新扫描和聚合，不自动运行新扫描；
- 用户点击“运行风险扫描”才创建扫描记录并强制失效风险域；
- 相同扫描按钮在 running 状态下不可重复提交；
- 证据详情按 tenant、workspace、request_ref 和授权摘要缓存；
- AI 自动咨询不阻塞页面刷新，页面刷新也不取消已开始的用户咨询。

## 12. 安全与治理边界

- 正式页面继续使用现有 Easy Auth 和 Entra 授权；
- tenant 与 workspace 范围全部由服务端推导和收窄；
- 客户界面使用“统一入口”，不直接展示底层网关产品名称；
- 扫描记录不保存正文、原始身份、密钥、任意查询或内部错误正文；
- 证据详情只展示现有允许的业务请求摘要和最终可见回答；
- 技术 ID 保持折叠并按需查看；
- `DF_FINOPS_ACTIONS_ENABLED`、外部模型路由和自动策略执行保持关闭；
- 运行扫描不等同于创建、批准或执行治理动作。

## 13. 组件边界

新增或调整以下边界：

- `FinOpsPortalShell`：共享标题、筛选、更新时间、证据抽屉和运营 AI；
- `CostManagementPage`：运营总览、成本和 ROI 导航；
- `RiskOperationsPage`：扫描状态、风险矩阵、优先事项和优化组合；
- `RiskScanStatus`：扫描操作与判定依据；
- `EvidenceSetDrawer`：多证据切换和请求详情；
- `FinOpsAskIntent`：上下文与默认问题生成；
- `StructuredAssistantAnswer`：结构化回答渲染；
- `RiskScanService`：确定性规则执行与扫描持久化；
- `EvidenceSelectionService`：按指标和规则选择代表证据。

避免继续扩大 `FinOpsPortal.jsx`、`router.py` 和 `assistant.py`。React 不计算风险、ROI 或财务结论；扫描服务不调用 AI。

## 14. 错误处理

- 扫描失败：保留上一次成功扫描，展示安全错误分类和重试；
- 规则数据不足：展示“样本不足”，不进入风险矩阵；
- 单个证据失效：保留其余证据并提示该请求不可用；
- AI 不可用：规则、扫描和证据仍完整可用；
- AI 结构化输出不合法：返回受控不可用状态，不渲染半截 JSON；
- 历史同步失败：当前咨询仍可继续，显示轻量同步提示；
- Redis 不可用：回退 SQL/查询服务并返回缓存不可用状态；
- SQL 扫描写入失败：本次扫描标记失败，不把临时计算结果伪装成已保存扫描。

## 15. 测试与验收

### 15.1 Python

- 每条规则只选择语义匹配的证据；
- 六类演示风险的首条证据引用具有区分度；
- 相同请求仅在确实同时支持两个判断时复用；
- 扫描记录保存规则版本、范围、样本和结果；
- 样本不足不生成风险；
- 扫描失败保留上一份成功结果；
- 跨 tenant/workspace 扫描和证据访问被拒绝；
- member 与 admin/owner 权限正确；
- 结构化 AI 输出只引用允许证据；
- AI 不得改变规则判定；
- additive SQL migration 幂等；
- 扫描不创建 FinOps action，也不依赖 action flag。

### 15.2 Node

- 所有特定证据按钮传对象和非空 `evidenceRefs`；
- 指标按钮不再统一回退最近请求；
- 证据抽屉可以切换 1–3 条请求并保留原因；
- 局部“问 AI”一次点击只自动发送一次；
- 不同指标生成不同默认问题；
- AI 回答按小标题、摘要和列表渲染；
- 历史文本回答兼容；
- AI 回答证据按钮保留真实引用；
- `finops` 与 `finops-risk` 导航、权限和旧入口归一正确；
- 缓存和自动刷新不触发扫描或 AI。

### 15.3 Playwright

- 左侧显示“成本管理”和“风险与优化”，无重复选中；
- 成本管理不再显示风险内部页签；
- 点击成本、缓存、时延、失败、未计价和 Token 证据，抽屉显示与该指标相符且不同的请求；
- 抽屉证据切换在桌面和移动端不遮挡顶部、tooltip 或关闭按钮；
- 点击不同位置“问 AI”后立即出现对应自动问题；
- AI 回答显示结论、判断依据、影响和建议等结构化区块；
- AI 回答“查看证据”打开本次回答引用的请求；
- “运行风险扫描”显示 running、completed 与上次成功回退状态；
- 扫描完成后显示规则数、样本数、发现数、覆盖率和策略版本；
- 页面刷新不自动创建扫描；
- 1366×768、1440×900 和移动端无覆盖、裁切或横向溢出。

### 15.4 演示验收

在 `demo-corpus` 完成：

1. 运行一次风险扫描；
2. 至少六项规则具有清晰的 triggered/clear/insufficient 状态；
3. 每条 triggered 风险可以解释观测值、阈值、样本和证据；
4. 六类证据点打开不同且语义相关的请求；
5. 缓存证据展示 miss/hit 对照；
6. 点击风险“问 AI”自动提问并返回结构化回答；
7. AI 回答的证据可以继续下钻；
8. 不出现底层网关产品名称、原始身份、密钥或内部错误正文；
9. 不开启或执行任何生产治理动作。

## 16. 发布边界

- 未经用户新的明确批准，不切换生产流量；
- 即使上线，`DF_FINOPS_ACTIONS_ENABLED` 仍保持 `0`。

## 17. 最终成功标准

面向 IT 人员演示时，可以用一条完整路径说明：

1. 成本管理回答当前成本、质量、效能和 ROI；
2. 风险与优化通过独立入口执行一次只读规则扫描；
3. 页面说明扫描范围、规则、阈值、样本和证据；
4. 每个判断打开自身对应的请求、指标和可见回答；
5. 点击“问 AI”自动针对当前判断发问；
6. AI 用规整的小标题和列表解释结论、依据、影响与建议；
7. AI 引用仍能回到具体证据；
8. 优化建议保持可审阅、可验证，但不会自动修改生产。
